# 운영·배포·복구

## 공개 전 외부 준비

카카오 앱, 호스팅, 도메인은 아직 없다. 유료 계약·호스팅 생성·도메인 구매·배포는 수행하지 않았다. 실제 운영 데이터·제휴 매장·브랜드도 미제공이다.

### 카카오

1. 발주자가 Kakao Developers에서 앱을 생성하고 최신 공식 카카오 로그인 절차·서비스 공개 요건을 확인한다.
2. 실제 대표 HTTPS 도메인을 Web 플랫폼에 등록하고 카카오 로그인을 활성화한다. 개발·운영 앱과 리디렉션 주소를 구분한다.
3. REST API 키를 `KAKAO_CLIENT_ID`에, 앱에서 활성화한 Client Secret을 `KAKAO_CLIENT_SECRET`에 환경 보안 설정으로 넣는다. 채팅으로 비밀값을 전송하지 않는다.
4. callback은 `https://실제도메인/accounts/kakao/login/callback/`. 로컬 공식 예시는 `http://localhost:8000/accounts/kakao/login/callback/`; 이 개발 서버는 8001이므로 카카오가 허용하는 개발 플랫폼·callback을 실제 앱에서 맞춰 등록해야 한다.
5. 공식 로그인 동의 설정을 최소 범위로 구성. 이 앱은 이메일을 총무 권한 기준으로 쓰지 않는다.
6. 최초 로그인·닉네임 동시 중복·로그아웃·원래 카페 화면 복귀·세션 만료를 실제 계정과 카카오톡 내부 브라우저로 시험한다. 지금 시험용 Django 세션은 이 단계의 완료 증거가 아니다.

필요한 외부 HTTPS 호스트는 `kauth.kakao.com`, `kapi.kakao.com`, `developers.kakao.com`. GitHub·패키지 레지스트리는 기존 인증·허용 정책을 사용한다. 환경 요구사항의 secret 값은 보안 설정에 입력한다. 현재 작업 중에 값을 요청하거나 가짜 키를 만들지 않았다.

### 호스팅·비용

최소 구성은 하나의 Linux 호스트 + 로컬 영속 디스크 + HTTPS reverse proxy + Gunicorn WSGI + 별도 worker이다. 호스팅 계약이 없으므로 정확한 요금은 미확인. 도메인·VM·디스크·백업 저장소 비용은 제공자 견적과 예상 동시 접속수를 확인한 후 발주자 승인 필요.

금지 구성: 임시 컨테이너 파일시스템에 DB 저장, 읽기 전용·휘발성 파일시스템, 여러 호스트가 같은 SQLite 파일을 네트워크로 공유, 요청 때만 실행되는 서버리스에서 영구 worker 없이 자동 취소를 주장하는 배포. 그런 환경이 필요하면 DB/작업 구성 변경을 협의한다.

DB와 비밀 설정은 앱 전용 OS 계정으로 소유하고 디렉터리 0700·파일 0600. 앱 서버 외 DB 파일 접근을 제한. 노출은 HTTPS proxy만; Gunicorn은 localhost에 바인딩한다. proxy는 요청 헤더·본문 크기와 접속률을 제한하고 능력 토큰 경로 전체를 access log에 저장하지 않는다. `X-Forwarded-Proto`를 신뢰하도록 Django 설정을 추가할 때는 프록시가 외부 값을 제거·덮어쓰는지 먼저 확인해야 한다. 지금 검증되지 않은 proxy trust는 설정하지 않았다.

프로덕션은 `.local/runtime.env`를 사용하지 않는다. `.env.example`의 운영값을 배포 보안 관리로 주입. `DJANGO_DEBUG=0`, `DEMO_MODE=0`, 정확한 ALLOWED_HOSTS, 무작위 SECRET_KEY, 영속 DATABASE_PATH 필수. 실제 데이터베이스에 seed_demo를 실행하지 않는다.

```sh
# 배포 환경변수가 주입된 프로젝트 디렉터리에서
.venv/bin/python manage.py migrate --noinput
.venv/bin/python manage.py check --deploy
.venv/bin/gunicorn coffee.wsgi:application --bind 127.0.0.1:8001 --workers 2 --worker-class sync --timeout 30 --no-control-socket
# 별도 감독 프로세스
.venv/bin/python manage.py expire_orders
```

supervisor/systemd 등 제공자 프로세스 관리로 앱·worker 모두 자동 재시작해야 한다. 위 명령은 개발 클라우드에서 Gunicorn WSGI 요청 검증을 했지만 실제 HTTPS 호스팅에서의 배포 검증은 아직이다. cookie Secure는 DEBUG=0에서 켜지므로 HTTPS가 필수이다. 운영 설정은 HTTPS 리디렉션과 1시간 HSTS를 기본 활성화한다. 실제 HTTPS proxy가 외부 X-Forwarded-Proto를 제거·덮어쓰는지 확인한 뒤에만 TRUST_HTTPS_PROXY=1을 지정한다. 검증 없이 신뢰 플래그를 켜면 안 된다.

## 최초 운영자·계정

운영 환경에서 단 한 번:

```sh
.venv/bin/python manage.py create_operator 운영자계정명
```

비밀번호는 getpass로 입력하며 Django password validation·hash를 사용한다. 기존 운영자가 있으면 생성 거부. 발주자만 보유한다. 판매자는 운영자 화면에서 비밀번호를 발급하고 매장과 연결한다. 발급 비밀번호는 최초 보안 채널로 전달한다. 회원가입을 공개하지 않는다. 판매자 삭제는 화면에서 처리한다.

비밀번호 분실: 서비스 OS 계정의 승인된 운영 작업으로 `manage.py changepassword 계정명` 사용. 일상 업무는 터미널을 요구하지 않는다. 계정 사고 시 `manage.py revoke_sessions 계정명`으로 서버 세션을 모두 해제한다. 카카오 플랫폼 토큰·연결 해제는 공식 앱 정책에 맞춰 별도로 수행한다. 현재 Kakao SocialToken의 원문 저장을 활성화하지 않았다.

## 백업·복원

```sh
.venv/bin/python manage.py backup_db /보안백업경로/coffee-날짜.sqlite3
```

이 명령은 SQLite online backup API로 DB를 일관되게 복사하고 integrity·foreign key를 검사한다. 같은 목적지가 있으면 덮어쓰지 않는다. 최소 운영 제안: 일일 백업과 배포 직전 백업, 오프호스트 암호화 저장. **보관 기간과 개인정보 삭제 정책은 공개 전 발주자 결정이 필요하므로 현재 자동 보관 정책을 확정하지 않았다.** 실제 운영 백업 서비스·저장소는 아직 설정하지 않았다.

복원 절차: 앱·worker 중지 → 현재 DB를 별도 backup으로 보존 → 백업 integrity/foreign key 검사 → 임시 복원 DB에서 코드 버전·마이그레이션·주문 개수와 알려진 주문 상태·합계를 확인 → DATABASE_PATH를 복원 파일로 교체 → 앱·worker 시작 → 미접수 만료 처리와 역할별 조회 확인. 잘못된 백업이면 보존한 현재 DB로 되돌린다. SECRET_KEY 등 환경 설정은 DB와 별도 안전하게 보관. 백업 DB에 세션·능력 토큰·개인정보가 있으므로 공개 아티팩트로 올리지 않는다.

현재 인스턴스에서 실제 DB backup→별도 파일 restore→integrity/foreign keys/전체 테이블 행 수 검증을 수행했다. 실제 운영 호스팅·오프호스트 저장소 복원은 미실행이다.

## 오류·업데이트

주문번호로 상태·시각·이력·version을 조회한다. 불확실한 전송은 새 주문을 만들지 말고 현재 DB 상태와 동일 idempotency key로 재시도. 화면의 ‘이전 요청 결과 확인·재시도’로 원 요청을 다시 확인한다. 원문 참여 이름·비밀번호·토큰을 로그에 복제하지 않는다. 서버 worker 실패·DB 잠금·디스크 잔량·백업 실패는 배포 제공자의 모니터링에 연결해야 한다.

의존성은 잠금 파일로 유지. 보안 공지 → 변경 영향 검토 → DB backup → 권한/동시성/기한 핵심 시험 → 브라우저 시험 → 배포. 실패 시 직전 코드와 DB backup으로 복구하되 이후 주문 유실 위험을 먼저 확인한다. 마이그레이션 뒤 코드만 이전 버전으로 되돌리는 것이 항상 안전하지 않다. Dependabot PR은 자동 병합하지 않는다.

## 남은 운영 결정

실제 카페·메뉴·브랜드·호스팅·대표 도메인, 영업 종료 시 주문 허용, 모집/마감 방 폐기, 개인정보 보관·삭제와 백업 보관. 별도 수령 확인·결제·알림톡·문자·OS 푸시·POS 기능은 추가하지 않았다.

Gunicorn 26의 기본 control socket은 이 클라우드의 읽기 전용 홈 디렉터리에 생성할 수 없으므로 `--no-control-socket`을 사용한다. 업무 HTTP 서버·worker 동작과 무관한 관리 인터페이스이며 이 MVP는 사용하지 않는다. 운영 체크에서 HSTS subdomain/preload 경고 2개는 실제 도메인·하위 도메인 정책 미정 때문에 남긴다. 전체 하위 도메인에 HTTPS를 강제하거나 preload 제출을 임의로 활성화하지 않았다.

### 사업자 없는 개인 등록 — 공식 안내 확인 (2026-10-12)

공식 https://developers.kakao.com/docs/latest/ko/app-setting/app 를 직접 확인했다. 앱 기본 정보에는 앱 이름·회사명·카테고리가 필수다. 회사명 입력과 사업자등록번호 인증은 서로 다른 항목이다. 개인의 회사명 입력값은 확인 없이 임의 안내하지 않는다.

공식 문서는 사업자등록번호가 없는 개인이나 단체의 앱도 개인 개발자 비즈 앱으로 전환할 수 있다고 명시한다. 조건은 앱 소유자의 본인인증과 카카오비즈니스 통합 서비스 약관 동의다. 경로는 우측 상단 프로필 > 계정 설정 > 본인인증, 이후 앱 > 일반 > 비즈니스 정보 > 개인 개발자 비즈 앱. 기본 앱 생성과 비즈 앱 전환은 구분해야 한다. 비즈니스 채널 연결은 별도 사업자 조건이 있으며 영차의 현재 확정 범위에 포함되지 않는다.

현재 사용자 화면에서 회사명만 요구하는지 사업자등록번호를 요구하는지 확인한 뒤 해당 단계만 안내한다. 키·비밀번호·본인인증 정보는 채팅으로 받지 않는다.

### 회사명 안내 정정 (2026-10-12)

사용자 화면의 ‘사업자 정보와 동일한 상호 또는 법인, 단체명’ 문구를 확인했다. 대화에서 회사명에도 서비스명 ‘영차’를 임의 입력하도록 안내한 것은 근거가 부족한 안내였으며 정정한다. 공식 FAQ https://developers.kakao.com/docs/ko/getting-started/faq 는 회사 등 기본 정보가 실제 서비스 정보와 동일해야 한다고 명시한다. 개인 개발자 허용 안내는 확인했으나 회사·단체 없는 개인이 해당 칸에 입력할 구체적인 값은 확인한 공식 문서에 명시되지 않았다. 본인 실명이나 서비스명으로 임의 대체하도록 다시 안내하지 않는다. 필요하면 사용자가 카카오 공식 지원에 개인의 회사명 입력 기준을 확인한다. 사업자등록이 필수라는 결론도 이 문구만으로 내리지 않는다. 로그인 방식 변경이나 새로운 유료·사업자등록 절차는 임의로 도입하지 않는다.
